**Page:** `/podcast` (archive/hub page)
**Date:** 10 July 2026
**Status:** Analysis only — no code changes

## 1. Current Implementation Details

### Architecture

| Aspect | Detail |
|---|---|
| **Route** | `src/app/(content)/podcast/page.tsx` — Next.js App Router |
| **Rendering** | Server component (page.tsx) wrapping a `"use client"` child (`PodcastSearch`) |
| **Data source** | `getAllEpisodes()` in `src/lib/podcast.ts` — reads and parses every `.mdx` file in `content/podcast/` at build time |
| **Episode count** | **814 MDX files** on disk |
| **Pagination** | **None.** All 814 episodes are rendered in a single page load |
| **Lazy loading** | **None.** No virtualisation, no intersection-observer-based loading, no "load more" |
| **Client payload** | All 814 episodes serialised as JSON props to the `PodcastSearch` client component (slug, title, episodeNumber, guest, guestCredential, description, publishDate, duration, pillar, type) |

### Client Component: `PodcastSearch`

Located at `src/components/features/podcast/PodcastSearch.tsx`.

- `"use client"` component receiving all episodes as props
- Client-side search (text matching against title/guest/description with scoring)
- Client-side pillar filter (coaching/nutrition/strength/recovery/community)
- Client-side type filter (interview/solo/panel/sarah-anthony)
- **Filters are URL-agnostic** — they use `useState` only, never update the URL via query params or hash
- **No filtered URLs are indexable** — crawlers only ever see the unfiltered state

### DOM Estimate

Per episode card in `PodcastSearch`:

| Element | Count |
|---|---|
| `<a>` (Link wrapper) | 1 |
| `<div>` containers | 3 |
| `<span>` (Badge) | 1 |
| `<span>` (type label) | 1 |
| `<h2>` (title) | 1 |
| `<p>` (guest name + credential) | 1 (+ 2 inner `<span>` when guest exists) |
| `<p>` (duration) | 1 |
| `<p>` (date) | 1 |
| **Subtotal per card** | **~12–14 nodes** |

**Total card DOM:** ~814 x 14 = **~11,400 DOM nodes** for episode cards alone.

Adding the page shell (header, footer, hero, search bar, filter buttons, social proof, podcast guides section, JSON-LD scripts): **estimated 11,800–12,200 total DOM nodes**.

Google flags pages with >1,500 DOM elements. This page exceeds that by 8x.

### JSON-LD Schema

The archive page emits three JSON-LD blocks:

1. **PodcastSeries** — `numberOfEpisodes: episodes.length` (814)
2. **ItemList** — capped at 20 items (good — only top 20 serialised)
3. **BreadcrumbList** — standard 2-level

The ItemList cap at 20 is well-designed. The PodcastSeries `numberOfEpisodes` is accurate and lightweight.

### Serialised JSON Payload to Client

Estimated per episode: ~400 bytes of JSON (slug, title, episodeNumber, guest, guestCredential, description, publishDate, duration, pillar, type).

**814 episodes x ~400 bytes = ~326 KB** of JSON serialised into the RSC payload. After gzip: ~60–80 KB. This is meaningful but not the primary concern — DOM size and rendering cost are worse.

### Sitemap

Podcast episodes occupy their own sitemap split (`/sitemap/2.xml`), generated by `buildPodcastSitemap()` in `src/app/sitemap.ts`. Each of the 814 episodes gets an entry, plus 380 dedicated transcript pages. Total podcast sitemap entries: **~1,194 URLs**.

## 2. Performance Risks Identified

### P0 — Critical

**A. Excessive DOM size (11,800+ nodes)**

All 814 episode cards render in the initial HTML. Google Lighthouse flags >1,500 elements; this page has 8x that threshold. Impact:
- Layout thrashing during paint
- Slow style recalculation on any interaction (search, filter)
- High memory consumption on mobile devices
- Degraded Interaction to Next Paint (INP) because every filter toggle re-renders 814 cards via React state change

**B. No pagination = full render on every visit**

The server component calls `getAllEpisodes()` and passes all 814 to the client. Even with build-time memoisation, the client receives and hydrates the full dataset on every page load.

### P1 — High

**C. Client-side-only filtering = invisible to crawlers**

Pillar and type filters use `useState` — they do not produce indexable URLs. A crawler cannot discover "all coaching episodes" or "all interview episodes" as distinct pages. This means:
- No `/podcast?pillar=coaching` or `/podcast/coaching` pages exist for Google to rank
- The 814 internal links on the archive dilute PageRank across all episodes equally, with no topical clustering signal
- AI search engines (Perplexity, ChatGPT Search, Claude) cannot answer "what coaching episodes does Roadman have?" from a dedicated URL

**D. Link dilution**

814 internal links from a single page. Google's link equity distribution divides the page's authority across all outbound links. At 814 links, each episode receives negligible equity from the archive page. Combined with no topical sub-indexes, the archive provides weak crawl signal for which episodes matter most.

**E. Crawl budget waste**

The archive page forces Googlebot to parse >11K DOM nodes to discover 814 links. With a 10-second rendering budget, Googlebot may truncate the page before reaching later episodes. Audio-only back-catalogue episodes (no transcript, no show notes) get equal sitemap and archive prominence as the 380 episodes with full transcripts.

### P2 — Medium

**F. No "load more" or progressive disclosure**

Every episode is in the initial HTML with no deferred loading. Users searching for a specific guest still download the full 326 KB JSON payload. Mobile users on poor connections pay the full cost even if they only want the latest 10 episodes.

**G. JSON payload size**

~326 KB raw (~60–80 KB gzipped) of episode data serialised into the page. Not catastrophic, but unnecessary when most users interact with <50 episodes per session.

**H. Transcript index page has the same problem**

`/podcast/transcripts` at `src/app/(content)/podcast/transcripts/page.tsx` renders all 380 transcript episodes in a single page with no pagination. Additionally, its JSON-LD `ItemList` includes all 380 entries (unlike the archive page which caps at 20). This is a secondary concern since 380 is less severe than 814, but the same pattern applies.

## 3. Existing Index Pages vs. Recommended

### Currently Exists

| Index Page | Route | Content |
|---|---|---|
| Podcast archive | `/podcast` | All 814 episodes, client-side filter/search |
| Transcript index | `/podcast/transcripts` | 380 episodes with `.txt` transcripts |
| Guest directory | `/guests` | ~148 unique guests, client-side filter by pillar/tag |
| Individual guest | `/guests/[slug]` | Per-guest page with all their episodes listed |
| Topic hubs | `/topics/[slug]` | 33 topic hubs (some reference episodes via `topicTags`) |
| Pillar pages | `/pillars/[slug]` | 5 pillar content hubs |

### Missing (Recommended)

| Recommended Index | Route | Purpose |
|---|---|---|
| **Pillar-filtered podcast pages** | `/podcast/coaching`, `/podcast/nutrition`, etc. | Dedicated indexable pages for episodes by pillar. Replaces invisible client-side filter with crawlable URLs. Each would list 28–384 episodes with pagination. |
| **Year-based archive** | `/podcast/2025`, `/podcast/2024`, etc. | Natural temporal segmentation. Splits 814 episodes into 8–10 manageable pages of 35–174 episodes each. Standard podcast archive UX. |
| **Episode type pages** | `/podcast/interviews`, `/podcast/solo` | 263 interviews and 496 solo episodes — distinct enough to warrant separate index pages. |
| **Series/season grouping** | No data field exists yet | Episodes lack a `series` field. Many podcasts group episodes into seasons or thematic series. Would require content enrichment. |

### What Already Works Well

- **Guest profiles** (`/guests/[slug]`) — each guest has a dedicated page with their episodes, key quotes, featured articles, and topic links. This is strong.
- **Topic hubs** (`/topics/[slug]`) — 33 topics, episodes tagged via `topicTags` field (407 of 814 episodes have tags). These provide thematic grouping.
- **Transcript library** (`/podcast/transcripts`) — dedicated index for the 380 episodes with full transcripts.
- **JSON-LD ItemList cap** — the archive wisely limits the structured data ItemList to 20 entries, avoiding schema bloat.

## 4. Specific Recommendations

### Priority 1 — DOM/Performance (impact: Core Web Vitals)

**R1. Paginate or virtualise the episode list**

Replace the single-page dump with server-side pagination. Options:
- **Server-side pagination** via `/podcast?page=2` or `/podcast/page/2` — 50 episodes per page, 17 pages total. Each page is a cacheable static page. Crawlers discover all episodes via next/prev links.
- **Hybrid: show 50 + "Load More" button** — initial page has 50 episodes (~700 DOM nodes for cards), clicking "Load More" appends 50 more. Maintains the single-page UX while keeping initial DOM small.
- **Virtual scrolling** (react-window or @tanstack/virtual) — renders only visible cards. Keeps the search UX intact but has SEO trade-offs since off-screen cards are not in the DOM for crawlers.

**Recommendation:** Server-side pagination with 50 episodes per page. This gives the best SEO profile (each page is indexable, manageable link count) while keeping DOM under 1,000 nodes for cards.

**R2. Cap the initial render**

If pagination is deferred, immediately cap `PodcastSearch` to show the first 50 episodes by default with a "Show all 814 episodes" button. This is a 30-minute change that cuts DOM by 93%.

### Priority 2 — SEO/Crawlability (impact: rankings, link equity)

**R3. Create pillar-filtered archive pages**

Generate static pages at `/podcast/coaching`, `/podcast/nutrition`, `/podcast/strength`, `/podcast/recovery`, `/podcast/community`. Each page:
- Has its own `<title>`, `<meta description>`, canonical URL
- Contains only episodes matching that pillar
- Gets its own ItemList JSON-LD (capped at 20)
- Links back to `/podcast` and to the corresponding `/pillars/[slug]` page
- Is included in `/sitemap/2.xml`

This turns invisible client-side filters into crawlable, rankable pages that can capture queries like "best cycling coaching podcast episodes."

**R4. Create year-based archive pages**

Generate static pages at `/podcast/2025`, `/podcast/2024`, etc. Standard podcast archive pattern. Splits link equity into temporal clusters and makes the archive navigable for users browsing by era.

**R5. Make filters update the URL**

If client-side filtering remains (alongside static pages), update the URL with `searchParams` so filtered states are shareable and bookmarkable: `/podcast?pillar=coaching&type=interview`. Not indexable (use `noindex` on filtered variants), but improves UX.

### Priority 3 — Content Quality Signal (impact: crawl efficiency)

**R6. Tiered sitemap priority for episodes**

Currently all 814 episodes have `priority: 0.6` in the sitemap. Differentiate:
- Episodes with transcripts + keyTakeaways + topicTags: `priority: 0.7`
- Episodes with transcripts only: `priority: 0.6`
- Audio-only back catalogue (no transcript, no enrichment): `priority: 0.4`

This signals to crawlers which episodes are worth deep-crawling.

**R7. Consider `noindex` for thin audio-only episodes**

The ~434 episodes without transcripts or enrichment (814 total minus 380 with transcripts) produce thin pages with only a title, description, and playback links. Evaluate whether these pages earn organic traffic. If not, `noindex,follow` would focus crawl budget on the 380 enriched episodes while preserving link equity flow.

**R8. Cap the transcript index ItemList**

`/podcast/transcripts` emits an ItemList JSON-LD with all 380 entries. Cap it at 20 (matching the archive page) to reduce schema payload.

## 5. Estimated Impact on Core Web Vitals

### Current State (Estimated)

| Metric | Estimate | Status |
|---|---|---|
| **LCP** | 2.5–3.5s | Amber — hero image + massive DOM delays paint |
| **INP** | 300–500ms | Poor — filtering 814 items triggers full React re-render |
| **CLS** | 0.05–0.1 | OK — layout is stable, but filter toggles may cause reflow |
| **Total DOM nodes** | ~12,000 | Fail — 8x Google's 1,500-element threshold |
| **HTML size** | ~800 KB–1 MB | Heavy — 814 cards + JSON-LD |

### After Pagination (R1 — 50 episodes per page)

| Metric | Estimate | Change |
|---|---|---|
| **LCP** | 1.5–2.0s | ~40% improvement |
| **INP** | <100ms | ~75% improvement — filtering 50 items is instant |
| **CLS** | <0.05 | Stable |
| **Total DOM nodes** | ~1,200 | 90% reduction |
| **HTML size** | ~150 KB | ~80% reduction |

### After Pillar Pages (R3)

Each pillar page contains 28–384 episodes. Even the largest (community at 384) benefits from pagination at 50/page. Crawlers get dedicated entry points per topic, improving topical authority signals.

### Net Effect

Implementing R1 (pagination) and R3 (pillar pages) together would:
- Move INP from "Poor" to "Good" range
- Reduce DOM by 90%
- Create 5 new indexable entry points that replace invisible filters
- Cut the per-page crawl cost by 80%, freeing budget for the 1,194 episode+transcript URLs in the sitemap
